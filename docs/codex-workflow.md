# Codex作業ワークフロー

このドキュメントは、個人制作プロジェクト「onile-shopping」でCodexを安全に使うための説明書です。
初心者でも分かるように、作業場所、GitHub、PR、サブエージェント、DB運用のルールをまとめています。

## 作業場所

Codexの作業場所は次に統一します。

```text

```

ローカルのリポジトリは次の場所を想定します。

```text

```

## GitHubリポジトリ

GitHubリポジトリは次です。

```text
Aliingar/onile-shopping
https://github.com/Aliingar/onile-shopping
```

## ブランチ運用

作業するときは、`main` ブランチを直接変更しません。
必ず作業用ブランチを作ります。

例:

```text
chore/setup-codex-workflow
feature/cart-page
fix/login-error
```

作業用ブランチで変更し、確認してからPull Requestを作ります。

## PR運用

PRはPull Requestのことです。
作業用ブランチの変更を `main` に入れてよいか確認するための場所です。

基本の流れは次です。

1. `main` から作業用ブランチを作る
2. 作業用ブランチで変更する
3. `git status` と `git diff` で変更内容を確認する
4. commitする
5. GitHubへpushする
6. Pull Requestを作る
7. 内容を確認してからmainへ反映する

## mainを直接触らない理由

`main` はプロジェクトの大事な本線です。
ここを直接変更すると、失敗した変更がすぐに本番用のコードへ混ざる可能性があります。

ブランチとPRを使うと、変更内容をあとから見直せます。
間違いに気づいたときも、どこを直せばよいか分かりやすくなります。

## サブエージェントの使い分け

作業内容に合わせて、次のサブエージェントを使います。

| サブエージェント | 担当 |
| --- | --- |
| `frontend` | HTML、CSS、JavaScript、画面、フォーム、ボタン、API接続、表示処理 |
| `backend` | Python/Flask、APIルート、バリデーション、エラー処理、MySQL接続処理、JSON、APIテスト |
| `database` | MySQL、テーブル設計、SQL案、Aiven注意点、DBeaver確認手順、主キー、外部キー、初期データ案 |
| `frontend_design` | 画面レイアウト、色、余白、ボタン、カード、スマホ対応、使いやすさ |

迷ったときは、何を変えたいかで選びます。
画面の動きなら `frontend`、APIなら `backend`、DB設計なら `database`、見た目なら `frontend_design` です。

## サブエージェントを確実に使うための頼み方

`AGENTS.md` は、プロジェクト全体のルールブックです。
`.codex/agents/*.toml` は、frontend、backend、database、frontend_design それぞれの専門担当の定義です。

Codexはサブエージェントを完全自動で必ず起動するとは限りません。
ただし、このリポジトリでは、メインエージェントが作業前に内容を分類し、必要な場合は自分からサブエージェントを明示的に起動するルールにします。
確実に使わせたいときは、今まで通り毎回のプロンプトで「○○サブエージェントを明示的に起動して」と書くと、担当をさらに分けやすくなります。

Codexには、作業前に次のように報告させます。

```text
サブエージェント判定: 使用する / 使用しない
使用するサブエージェント: frontend / backend / database / frontend_design / 複数 / なし
選んだ理由: ○○
今回の作業範囲: ○○
変更してよいファイル: ○○
変更してはいけないファイル: ○○
危険操作をしないことの確認
```

hooksはサブエージェント起動用ではありません。
hooksは、秘密情報を表示しそうな操作や危険コマンドを見つけるための安全チェック用です。

プロンプト例:

```text
frontend サブエージェントを明示的に起動して、商品一覧画面の表示だけ確認してください。APIとDBは変更しないでください。
```

```text
backend サブエージェントを明示的に起動して、商品APIの処理だけ確認してください。フロントとDBスキーマは変更しないでください。
```

```text
database サブエージェントを明示的に起動して、MySQLのテーブル設計案だけ作ってください。AivenやDBeaverには接続しないでください。
```

## サブエージェントを自動で選ばせる運用

毎回ユーザーがサブエージェント名を書かなくても、メインエージェントは作業前に内容を分類します。
`AGENTS.md` は作業前に読むルールブックで、`.codex/agents/*.toml` は専門担当の定義です。
hooksはサブエージェント起動用ではなく、安全チェック用です。

作業前に「使用するサブエージェント」を報告させる理由は、Codexがどの範囲を担当するのかを人間が確認しやすくするためです。
複数分野にまたがる作業では、複数のサブエージェントを使い、最後にメインエージェントが結果をまとめます。

例:

```text
商品一覧画面を見やすくしてください
```

この場合、メインエージェントは `frontend_design` または `frontend` を選びます。

```text
商品APIのエラーを直してください
```

この場合、メインエージェントは `backend` を選びます。

```text
注文テーブルを考えてください
```

この場合、メインエージェントは `database` を選びます。

```text
トップページの見た目を改善して、必要ならHTML/CSSへ反映してください
```

この場合、メインエージェントはまず `frontend_design` で方針を作り、必要なら `frontend` で実装します。

## フロントエンドデザインの作り方

フロントエンドのデザインは、いきなりコードを書かずに、まずデザイン案を作ります。
先に雰囲気や方向性を決めると、あとからHTML、CSS、JavaScriptを直すときに迷いにくくなります。

役割は次のように分けます。

- `@creative-production`: 0から1を作る係です。アプリの雰囲気、方向性、画面のラフ案、ユーザーに与える印象、デザインコンセプトを考えます。
- `@product-design`: 1から100に磨く係です。画面レイアウト、UI部品、色、余白、ボタン、カード、スマホ対応、使いやすさ、画面遷移、実装しやすいUI仕様まで具体化します。
- `frontend_design` サブエージェント: 完成したデザイン仕様を実装につなげる係です。必要な画面、変更理由、確認方法を整理します。

デザインPRと実装PRは分けると安全です。
デザインPRでは「どんな画面にするか」を確認し、実装PRでは「実際にHTML、CSS、JavaScriptへ反映する変更」を確認します。
これにより、デザイン案が固まる前にアプリ本体を大きく変更してしまうことを防げます。

Codexに渡す例文:

```text
@creative-production を使って、このECサイトのトップページのデザイン方向性を0から1で考えてください。まだコードは変更しないでください。
```

```text
@product-design を使って、先ほどのデザイン方向性を実装しやすいUI仕様まで具体化してください。まだコードは変更しないでください。
```

```text
frontend_design サブエージェントを使って、完成したUI仕様をHTML/CSSへ反映する実装計画を作ってください。APIやDBは変更しないでください。
```

## DB運用

このプロジェクトのDBはMySQLです。
MySQL DBはAiven Consoleで作る前提です。
接続やSQL実行は、人間がDBeaverを使って行う前提です。

Codexは実DBに勝手に接続しません。
CodexはAiven ConsoleやDBeaverを勝手に操作しません。
CodexはSQL案や確認手順を作る役割にします。

## DB削除・テーブル削除の危険性

DB削除やテーブル削除は、とても危険です。
一度消すと、商品情報、ユーザー情報、注文情報などが戻せなくなる可能性があります。

次のSQLは特に注意が必要です。

```sql
DROP TABLE table_name;
TRUNCATE TABLE table_name;
DELETE FROM table_name;
ALTER TABLE table_name DROP COLUMN column_name;
```

これらを書く必要があるときは、必ず「人間確認必須」と書き、人間が内容を確認してから実行します。
Codexが勝手に実行してはいけません。

## Codexに渡すプロンプト例

フロントエンドを直したいとき:

```text
frontendサブエージェントで、商品一覧画面のボタン表示を確認してください。
DBや秘密情報には触れず、変更後に確認方法を初心者向けに説明してください。
```

バックエンドを直したいとき:

```text
backendサブエージェントで、商品取得APIのエラー処理を確認してください。
.envは開かず、既存APIを壊さない方針でお願いします。
```

DB設計を相談したいとき:

```text
databaseサブエージェントで、MySQLの商品テーブル案を作ってください。
実DBには接続せず、DBeaverで確認する手順も説明してください。
```

デザインを整えたいとき:

```text
frontend_designサブエージェントで、スマホ画面の余白とボタン配置を見直してください。
API仕様やDBは変更せず、変更理由と確認場所を書いてください。
```

## 先生や他の人に説明する短文

このプロジェクトでは、`main` を直接変更せず、作業用ブランチとPull Requestで安全に変更を確認します。
Codexの作業範囲をフロントエンド、バックエンド、DB、デザインに分け、秘密情報や実DBには勝手に触れないルールをリポジトリに残しています。
